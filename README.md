# Ldrbrd

A REST API server where students publish arbitrary JSON from their own apps,
scoped to their instructor's course, and anyone can read it back.

Built with Django 5.2 + [django-ninja](https://django-ninja.dev/), authenticated
entirely through Canvas.

---

## How it fits together

```
Canvas (OIDC)  ──►  sign in  ──►  registered Ldrbrd user
                                       │
                        superuser promotes to staff (Django admin)
                                       │
                                       ▼
                              staff user creates a Course
                                       │
                        shares  <base>/join/<join_token>
                                       │
                                       ▼
                       student joins, registers an App
                             (gets an autogenerated secret_key)
                                       │
                          instructor approves the App
                                       │
                                       ▼
   PUT /<instructor>/<course>/<app>?secret_key=…   ← writes  (key required)
   GET /<instructor>/<course>/<app>                ← reads   (world readable)
```

Roles map onto Django's own flags: **superuser** = Django admin, **staff** =
instructor (may create courses), everyone else is a student.

## Canvas authentication

Canvas is the only way in. There is no local signup, and no password ever
touches Ldrbrd.

Canvas is not a conforming OpenID Connect provider — it does not publish a
`/.well-known/openid-configuration`, and its userinfo endpoint
(`/api/v1/users/self`) returns Canvas's own shape rather than OIDC claims.
Two things bridge that gap:

1. **A discovery shim.** Ldrbrd serves
   `/.well-known/canvas-openid-configuration`, generated from `CANVAS_BASE_URL`
   (see `accounts/views.py`). allauth's OIDC adapter fetches that instead.

2. **The [`hcientist/django-allauth`](https://codeberg.org/hcientist/django-allauth/src/branch/overridable_oidc_conf)
   fork**, branch `overridable_oidc_conf`. Ldrbrd depends on two things the
   upstream OIDC provider does not offer:

   | fork setting     | why Ldrbrd needs it                                             |
   | ---------------- | --------------------------------------------------------------- |
   | `uid_field`      | Canvas userinfo has `id`, not the OIDC-standard `sub`           |
   | `openid_config`  | per-app overrides merged over the fetched discovery document     |

   `openid_config` is the operator escape hatch: repoint `token_endpoint` at a
   proxy, or `userinfo_endpoint` at a staging Canvas, without a redeploy.

`accounts/adapters.py` then maps Canvas's `{id, name, short_name, login_id,
primary_email}` onto a Django user.

## Setup

```bash
python3 -m virtualenv .venv          # `python3 -m venv` needs python3-venv
./.venv/bin/pip install -r requirements.txt
cp .env.example .env                 # then fill in the Canvas credentials
./.venv/bin/python manage.py migrate
./.venv/bin/python manage.py createsuperuser
./.venv/bin/python manage.py runserver
```

In Canvas, create a developer key (**Admin → Developer Keys → + API Key**) and
set its redirect URI to:

```
<LDRBRD_BASE_URL>/accounts/oidc/canvas/login/callback/
```

Put the key's id and secret in `.env` as `CANVAS_CLIENT_ID` /
`CANVAS_CLIENT_SECRET`.

Interactive API docs live at `/api/docs` (management) and `/docs` (data).

## The data plane

Writes need the app's `secret_key` in the querystring and only work once the
instructor has approved the app. Reads need nothing at all.

```bash
# publish (student's app)
curl -X PUT "https://ldrbrd.example.edu/prof/cs-101/my-game?secret_key=$KEY" \
     -H 'Content-Type: application/json' \
     -d '{"scores":[{"who":"ada","points":42}]}'

# read (anyone)
curl https://ldrbrd.example.edu/prof/cs-101/my-game

# read every app in the course at once
curl https://ldrbrd.example.edu/prof/cs-101
```

| method   | path                                | auth        | effect                              |
| -------- | ----------------------------------- | ----------- | ----------------------------------- |
| `GET`    | `/<instructor>/<course>/<app>`      | none        | read the document                   |
| `GET`    | `/<instructor>/<course>`            | none        | read every app's document           |
| `PUT`    | `/<instructor>/<course>/<app>`      | secret_key  | replace the document                |
| `POST`   | `/<instructor>/<course>/<app>`      | secret_key  | alias for `PUT`                     |
| `PATCH`  | `/<instructor>/<course>/<app>`      | secret_key  | shallow-merge into a JSON object    |
| `DELETE` | `/<instructor>/<course>/<app>`      | secret_key  | reset the document to `{}`          |

Any JSON value is accepted — object, array, string, number, `true`/`false`, or
`null` — capped at `LDRBRD_MAX_PAYLOAD_BYTES` (1 MiB by default).

**All stored data is world readable.** That is the intended design; there is
deliberately no UI to change it.

## Usage leaderboard

`/top` ranks every registered app by how much traffic it is getting. It is
public, like the data it summarises, and the filter round-trips through the
querystring so a narrowed view is a shareable link.

```
/top                                    every app, most activity first
/top?course=prof/cs-101                 one course
/top?course=12&sort=writes              by id, ranked by writes
```

`sort` is one of `total` (default), `reads`, `writes`, `recent`. Because a
ranked bar chart is read as monotonic, the bar encodes whatever the ranking
encodes: `total` draws the reads+writes stack, `reads`/`writes` draw that one
series, and `recent` keeps the stack since recency is not a magnitude.

Apps that have never been touched still appear, at the bottom, with zeroes —
"registered but unused" is a fact worth showing.

The same data as JSON:

```bash
curl https://ldrbrd.example.edu/api/top
curl "https://ldrbrd.example.edu/api/top?course=prof/cs-101&sort=reads"
```

Counting happens on the public data endpoints: a `GET` of one app is one read,
a course-wide `GET` is one read for each app it returned, and each accepted
`PUT`/`POST`/`PATCH`/`DELETE` is one write. Rejected requests — bad key,
unapproved app — are not counted. Tallies live in `courses.AppUsage` and move
through `F()` expressions, so concurrent requests cannot lose an increment.

Two consequences worth knowing: every public read costs one small `UPDATE`
(fine at classroom scale, but it is a write on the read path), and the counters
are cumulative totals, not a time series — there is no per-day history to chart.

## The management API

Session-authenticated — sign in through Canvas first. Because ninja's
`django_auth` is cookie-based, unsafe methods need an `X-CSRFToken` header.

| method   | path                                | who                      |
| -------- | ----------------------------------- | ------------------------ |
| `GET`    | `/api/top`                          | **public** (no auth)     |
| `GET`    | `/api/me`                           | any signed-in user       |
| `GET`    | `/api/courses`                      | courses you teach or joined |
| `POST`   | `/api/courses`                      | staff only               |
| `GET`    | `/api/courses/{id}`                 | instructor or enrolled   |
| `PATCH`  | `/api/courses/{id}`                 | instructor               |
| `DELETE` | `/api/courses/{id}`                 | instructor               |
| `POST`   | `/api/courses/join`                 | any signed-in user       |
| `GET`    | `/api/courses/{id}/roster`          | instructor               |
| `GET`    | `/api/courses/{id}/apps`            | instructor: all; student: own |
| `POST`   | `/api/courses/{id}/apps`            | enrolled student         |
| `GET`    | `/api/apps`                         | your apps, with secrets  |
| `GET`    | `/api/apps/{id}`                    | owner or instructor      |
| `POST`   | `/api/apps/{id}/approve`            | instructor               |
| `POST`   | `/api/apps/{id}/unapprove`          | instructor               |
| `POST`   | `/api/apps/{id}/rotate-secret`      | owner or instructor      |
| `DELETE` | `/api/apps/{id}`                    | owner or instructor      |

A course's `join_url` and an app's `secret_key` are nullable response fields,
populated only for the people entitled to see them.

## Promoting an instructor

Django admin → **Users** → tick the user → **Promote to staff (may create
courses)**. Only superusers may run that action; demotion refuses to touch
superusers so the admin site can never be locked out.

Note that `is_staff` is Django's own admin-access flag, so a promoted
instructor can also reach `/admin/` — they will see nothing there without model
permissions, but the login page will accept them.

```bash
./.venv/bin/python manage.py test
```

84 tests cover the Canvas OIDC wiring and the fork-specific settings, the
Canvas-to-Django user mapping, the promotion flow, per-role visibility of join
links and secret keys, approval gating, the data plane's round trips and
rejections, and the leaderboard's counting, filtering and bar scaling.
